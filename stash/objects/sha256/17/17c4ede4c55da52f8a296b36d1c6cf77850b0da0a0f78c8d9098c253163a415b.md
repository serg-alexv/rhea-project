## 1. Результат

На локальной машине сохранилась существенная инженерная работа: отдельный OpenBSD pipeline, patch для compile-smoke, упаковка и проверка handoff, аудит резервного копирования, диагностические логи и VM builder. Первоначальная оценка всего MBSD как набора публичных заглушек была неполной. [L2–L4]

Однако конкретный найденный RAM candidate **не является доказательством собственного MT7981-ядра**. По переданному локальному протоколу его подписанный manifest описывает stock OpenBSD 7.9 arm64, явно исключает использование локального исходного дерева для включённых бинарников и указывает, что MT7981-stubs в них отсутствуют. Копии и handoff-подпись проверены локальным агентом; независимая аутентификация upstream остаётся неустановленной. [L4]

Шесть бинарников Blueshoes B0 перечислены в историческом manifest, но не найдены в обследованной области. Архив `agent_transfer_bundle.tar.gz` содержит пять исходных/тестовых файлов и пять служебных файлов с префиксом `._`; исполняемых файлов из manifest в нём нет. [L4]

Сборка собственного MBSD-ядра, загрузка на GL-MT3000, работа интерфейсов и восстановление после отказа **не установлены представленными доказательствами**. Это ограниченный вывод о проверенном корпусе, а не утверждение, что таких результатов нигде не существует.

Общая архитектурная «крыша» уже существует на GitHub: ветка `rhea-project-v2` репозитория `timelabs-npo/rhea-project`. На проверенном commit она объединяет план из восьми стадий, но сохраняет `DESIGN_ONLY`, допускает только подготовку Stage 01 и явно оставляет реализацию LIT в отдельном Omnia worktree. Раздельные репозитории компонентов сами по себе не противоречат этой модели. [G1–G4]

## 7. Что это меняет в сравнении BSDRP и MBSD

| Критерий | BSDRP | MBSD с учётом локальных следов |
| --- | --- | --- |
| Доказательная база | Публичный релиз 2.2; FreeBSD, FRR/Bird, описанные routing/HA/QoS возможности | Публичные исходники плюс отдельный локальный pipeline, transfer integrity и отрицательные readiness gates |
| Найденный загрузочный артефакт | Публикуемые appliance images | Конкретный найденный RAM candidate описан как stock OpenBSD, custom build прямо исключён |
| GL-MT3000 | Общий aarch64 target не доказывает поддержку платы | Поддержка собственным kernel/runtime не установлена |
| Операционный риск | A/B, RO root и hashes требуют самостоятельной оценки rollback/authentication | Потеря привязки «source → build → artifact → target run» и смешение разных MBSD lanes |

BSDRP остаётся более зрелым routing reference. Его требования — 4 ГБ носителя и 1 ГБ RAM, с 512 МБ для виртуальных тестов; релиз 2.2 использует snapshot FreeBSD main. Это не делает его автоматически подходящей прошивкой GL-MT3000. [B1–B2]

Предыдущий статический разбор BSDRP отмечал неполные bootonce/failed-boot механизмы, незавершённый secure config apply и проблемы в arm64 dispatch upgrade-скрипта; это результаты чтения исходников, не повторённые аппаратные тесты. [B3–B5]

Исправляется прежнее чрезмерное обобщение: инженерная работа MBSD не сводится ко всем публичным stubs. При этом локальный handoff не устраняет замечания к отдельному публичному build path и не закрывает аппаратные milestones. Решение о kernel/BSP не принимается этим evidence-отчётом и не расширяет текущий Stage 01.

## 8. Как удержать проекты под одной крышей

Рекомендуемая модель соответствует уже опубликованному v2 design:

| Что имеет общего владельца | Где находится | Чего это не означает |
| --- | --- | --- |
| Архитектура, стадии и границы полномочий | `rhea-project`, ветка `rhea-project-v2`, `v2/` | Что все реализации необходимо физически скопировать сюда |
| Версии наблюдённых источников и evidence | Существующие Stage 01 registry/index плюс dated reports | Что observed remote HEAD автоматически становится accepted dependency |
| Реализация и component tests | Репозиторий соответствующего компонента | Что успешный component test квалифицирует весь продукт |
| Будущая LIT-реализация | Additive Rust в `omnia-vault/supervisor`, отдельный worktree от frozen baseline | Что можно запустить legacy entrypoints или начать Stage 03 до CON/VAL gates |
| Проверка совместной работы | Отдельно принятые contracts и независимые composition receipts | Что родство имён или подпись файла дают routing/storage authority |
| Binary custody | Отдельное хранилище артефактов с manifest/digest/access policy | Что обычный Git обязан хранить VM и credential artifacts |

Для сборки конкретной версии системы в будущем нужен точный набор `repo + commit + path + contract identity + qualification evidence`. Регистр наблюдений уже есть; его не следует заменять очередным конкурирующим «source of truth». Отдельное утверждение состава сборки выполняется только после соответствующих gates. Сейчас допустимо уточнять source identities и различать legacy, candidate и admitted input. [G1–G4]

Свежая ветка v2 прямо указывает: `implementation_created: false`, `source_relocation: false`, `legacy_entrypoints_allowed: false`; активная работа — `01_contracts: prepare, do not declare freeze`. Все 55 записанных gates — `NOT_EXECUTED`; executable runtime enforcement не реализован. Это проверенные **значения файлов состояния**, а не независимая оценка всех работ за пределами ветки. [G4]

Публичная v2-ветка также продолжает указывать два missing normative inputs. Отдельная Omnia audit-ветка уже существует и обновлена, поэтому следующий контрактный шаг — сопоставить её точные файлы с этими требованиями. Сообщение о публикации или наличие audit branch само по себе не означает, что CON-02 выполнен. [G2, G4, G8]

## 10. Системная причина расхождений

Рабочая гипотеза по представленным материалам: основной сбой — потеря ограничений при handoff и неопределённый владелец актуального состояния, усиленные разделением source, artifact и execution evidence между инструментами.

Конкретный пример: подписанный bundle сохраняет `ram_boot_ready: false`, однако поздняя инструкция предлагает transfer/NAND write для того же candidate. Другой пример: acquisition-script GO рискует интерпретироваться как readiness ОС. Истории показывают такие переходы формулировок; они не доказывают мотивы агентов и не делают каждое повторное сообщение независимым событием. [L3–L4]

Минимальная дисциплина handoff: передавать вместе artifact digest, source/build linkage или UNKNOWN, назначение, допустимые операции, незакрытые gates и ссылки на первичные receipts. Подпись переносит утверждение; независимая проверка устанавливает доверие; target execution доказывает поведение. Эти уровни должны оставаться раздельными даже под общей RHEA-крышей.
